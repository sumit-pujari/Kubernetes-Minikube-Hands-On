# ☸️ Kubernetes Pods

> **Deploy Your First Application**
>
> In this section we move from Kubernetes theory to practical Kubernetes.
> We will learn what a Pod is, why Kubernetes uses Pods instead of directly
> managing containers, how to install and use `kubectl`, how to create a
> local Kubernetes cluster using Minikube, and how to deploy our first
> application.

---
## 1. From Containers to Kubernetes

Before Kubernetes, we learned how to run applications using containers.

For example, using Docker:

```text
Application
     |
     ↓
 Docker Image
     |
     ↓
 Container
```
Docker makes it easy to:

- Build container images
- Run containers
- Stop containers
- Remove containers
- Manage individual containers

But when we have many containers, we need an orchestration platform.
```
                    Kubernetes
                        |
       ┌────────────────┼────────────────┐
       ↓                ↓                ↓
   Containers       Containers       Containers
```
Kubernetes provides capabilities such as:

- Cluster management
- Auto healing
- Auto scaling
- Scheduling
- Networking
- Service discovery
- High availability
- Enterprise-level workload management

The first practical object we need to understand in Kubernetes is the
Pod.

---
## 2. Container vs Pod

One of the most important beginner concepts is understanding the
difference between a Container and a Pod.

A common mistake is:
```
Pod = Container
```
This is incorrect.

Instead:
```
Kubernetes
    |
    ↓
   Pod
    |
    ↓
Container(s)
```
A Pod is a Kubernetes abstraction that provides an environment in which
one or more containers run.

---
## 3. What is a Pod?

A Pod is the smallest deployable unit in Kubernetes.

When we deploy an application in Kubernetes, we normally don't directly
deploy the container.

Instead:
```
Application
     |
     ↓
   Pod
     |
     ↓
Container
```
The Pod provides the Kubernetes-level abstraction around the container.

**Simple definition**

A Pod is the smallest deployable unit in Kubernetes and represents
one or more containers that are deployed together.

---
## 4. Why Does Kubernetes Use Pods?

You may ask:

If Kubernetes ultimately runs containers, why doesn't Kubernetes
directly manage containers?

The answer is that Kubernetes needs a higher-level abstraction around
containers.

A Pod allows Kubernetes to manage:

- Container configuration
- Networking
- Storage
- Lifecycle
- Scheduling
- Resource configuration

Instead of managing only:
```
Container
```
Kubernetes manages:
```
Pod
 |
 ├── Container
 ├── Network
 └── Storage
```
This makes the Pod a useful unit for Kubernetes scheduling and
management.

---
## 5. Pod as a Wrapper Around Containers

You can think of a Pod as a wrapper around one or more containers.

For a simple application:

        Pod
         |
         ↓
    ┌─────────┐
    │Container│
    └─────────┘

For a multi-container Pod:
```
             Pod
              |
       ┌──────┴──────┐
       ↓             ↓
 Application      Sidecar
 Container        Container
```
The containers inside the same Pod are tightly coupled.

They can share certain Pod-level resources such as networking and
storage.

---
## 6. Pod Networking

A Pod receives its own network identity/IP address within the cluster.

For example:
```
Pod
 |
 └── IP: 10.x.x.x
```
If a Pod contains multiple containers, those containers share the
Pod's network namespace.

Therefore, containers inside the same Pod can communicate with each
other using:
```
localhost
```
Conceptually:
```
             Pod
              |
      ┌───────┴────────┐
      ↓                ↓
 Container A       Container B
      |                |
      └──── localhost ─┘
```
This is one of the important differences between simply running
independent containers and placing containers inside the same Pod.

---
## 7. Pod and Container Relationship

The relationship can be remembered as:
```
Kubernetes Cluster
       |
       ↓
      Pod
       |
   ┌───┴────┐
   ↓        ↓
Container Container
```
Important

A Pod can contain:
```
1 container
```
or:
```
multiple containers
```
However, in most normal applications, a Pod commonly contains a
single main application container.

Multiple containers are generally used when the containers are
closely related and need to share the same Pod environment.

---
## 8. What is kubectl?

kubectl is the command-line tool used to interact with Kubernetes
clusters.

Think of it as the primary CLI through which you communicate with
Kubernetes.
```
Developer
    |
    ↓
 kubectl
    |
    ↓
Kubernetes API
    |
    ↓
Kubernetes Cluster
```
For example:
```
kubectl get pods
```
This asks Kubernetes:

"Show me the Pods in the current namespace."

---
## 9. kubectl vs Docker CLI

If you have worked with Docker, you may know commands such as:
```
docker ps
docker run
docker stop
docker rm
```
Kubernetes provides:
```
kubectl get pods
kubectl create
kubectl delete
kubectl logs
kubectl describe
```
The idea is similar, but the scope is different.

| Docker CLI         | kubectl                         |
| ------------------ | ------------------------------- |
| Works with Docker  | Works with Kubernetes           |
| Manages containers | Manages Kubernetes resources    |
| `docker ps`        | `kubectl get pods`              |
| `docker run`       | Kubernetes resource definitions |
| `docker logs`      | `kubectl logs`                  |
| `docker stop`      | `kubectl delete`                |

## 10. Installing kubectl

Before interacting with a Kubernetes cluster, we need kubectl.

The official Kubernetes documentation provides installation instructions
for different operating systems.

Common platforms include:

- Linux
- macOS
- Windows

You should choose the correct installation instructions according to
your operating system and CPU architecture.

After installation, verify it:
```
kubectl version --client
```
If the installation is successful, the command should return the
installed client version.

## 11. What is Minikube?

Minikube is a tool that allows you to run a Kubernetes cluster
locally.

Instead of creating a Kubernetes cluster on AWS or another cloud
provider, you can run a cluster on your own computer.

Conceptually:
```
Your Laptop
     |
     ↓
 Minikube
     |
     ↓
Kubernetes Cluster
```
This is extremely useful for learning Kubernetes.

---
## 12. Why Use Minikube?

If you are learning Kubernetes, you don't necessarily need to create
a production Kubernetes cluster on AWS.

Cloud environments may involve:

- EC2 costs
- EKS costs
- Networking costs
- Storage costs
- Load balancer costs

For learning purposes, a local cluster is usually sufficient.
```
Learning Kubernetes
       |
       ↓
 Local Cluster
       |
       ↓
   Minikube
```
Therefore, Minikube is a convenient option for beginners.

---
## 13. Other Local Kubernetes Options

Minikube is not the only way to run Kubernetes locally.

Other options include:

**1. Minikube**

Good for:

- Beginners
- Learning Kubernetes
- Basic local experiments
  
**2. Kind**

Kind = Kubernetes IN Docker

Kind runs Kubernetes nodes using Docker containers.

It is useful for:

- Advanced local Kubernetes testing
- Multiple clusters
- Kubernetes development
- CI environments
  
**3. K3s**

K3s is a lightweight Kubernetes distribution.

It is useful where a smaller/lighter Kubernetes installation is desired.

**4. MicroK8s**

MicroK8s is another lightweight Kubernetes option.

---
## 14. Minikube Architecture

Minikube can create a local Kubernetes cluster.

For basic learning, it commonly creates a single-node cluster.

Conceptually:

                Laptop
                  |
               Minikube
                  |
                  ↓
          ┌───────────────┐
          │ Kubernetes    │
          │     Node      │
          │               │
          │ Control Plane │
          │      +        │
          │ Worker        │
          │ Components    │
          └───────────────┘

In production, we normally use multiple nodes for availability and
scalability.

       Production Cluster

       ┌─────────────┐
       │Control Plane │
       └──────┬──────┘
              |
      ┌───────┼────────┐
      ↓       ↓        ↓
    Node 1  Node 2   Node 3

Minikube is intended for local development/learning rather than
representing a production-grade highly available cluster.

---
## 15. Creating a Local Kubernetes Cluster

After installing Minikube, the basic command is:
```
minikube start
```
This starts a local Kubernetes cluster.

The general flow is:
```
Install kubectl
       |
       ↓
Install Minikube
       |
       ↓
minikube start
       |
       ↓
Kubernetes Cluster
       |
       ↓
kubectl
       |
       ↓
Interact with Cluster
```
## 16. Checking the Cluster

After starting Minikube, verify that Kubernetes is working.

Use:
```
kubectl get nodes
```
Example:
```
NAME       STATUS   ROLES           AGE   VERSION
minikube   Ready    control-plane   ...   ...
```
The important thing is:
```
STATUS = Ready
```
This tells us that the node is available to Kubernetes.

## 17. Writing Your First Pod YAML

Kubernetes resources are commonly defined using YAML manifests.

Example:
```text
apiVersion: v1
kind: Pod

metadata:
  name: nginx-pod

spec:
  containers:
    - name: nginx
      image: nginx
      ports:
        - containerPort: 80
```
This YAML tells Kubernetes how we want the Pod to be configured.

---
## 18. Docker Command vs Pod YAML

With Docker, we might run NGINX using:
```
docker run -d --name nginx -p 80:80 nginx
```
This command tells Docker:
```
Run nginx
    |
    ├── Detached mode
    ├── Name = nginx
    └── Port = 80:80
```
In Kubernetes, we describe the desired state using YAML:
```
apiVersion: v1
kind: Pod

metadata:
  name: nginx-pod

spec:
  containers:
    - name: nginx
      image: nginx
      ports:
        - containerPort: 80
```
So the conceptual difference is:
```
Docker
   ↓
Imperative command

Kubernetes
   ↓
Declarative configuration
   ↓
YAML
```
---
## 19. Creating a Pod

Once the YAML file is ready, suppose it is saved as:
```
pod.yaml
```
Create the Pod:
```
kubectl create -f pod.yaml
```
Here:
```
kubectl
   ↓
create
   ↓
-f pod.yaml
   ↓
Create resource from YAML
```
Another commonly used approach is:
```
kubectl apply -f pod.yaml
```
apply is especially useful when you want to create or update resources
declaratively.

---
## 20. Checking Pods

After creating the Pod:
```
kubectl get pods
```
Example:
```
NAME        READY   STATUS    RESTARTS   AGE
nginx-pod   1/1     Running   0          10s
```
| Column     | Meaning                                       |
| ---------- | --------------------------------------------- |
| `NAME`     | Name of the Pod                               |
| `READY`    | Number of ready containers / total containers |
| `STATUS`   | Current Pod status                            |
| `RESTARTS` | Number of container restarts                  |
| `AGE`      | How long the Pod has existed                  |

---
## 21. Getting Detailed Pod Information

Use:
```
kubectl get pods -o wide
```
The -o wide option displays additional information.

For example, it can show:

- Pod IP
- Node on which the Pod is running
- Additional Pod information

Example:
```
NAME        READY   STATUS    IP           NODE
nginx-pod   1/1     Running   10.x.x.x     minikube
```
---
## 22. Describing a Pod

For detailed information about a specific Pod:
```
kubectl describe pod nginx-pod
```
This is one of the most useful debugging commands.

It can show information such as:

- Pod metadata
-Containers
- Images
- Events
- Node
- Conditions
- Mounts
- Networking information
- Scheduling information

For example:
```
kubectl describe pod <pod-name>
```
When a Pod is not starting correctly, describe is one of the first
commands you should try.

---
## 23. Accessing the Kubernetes Node

When using Minikube, you can access the local Kubernetes environment
using:
```
minikube ssh
```
This opens a shell inside the Minikube environment.

Conceptually:
```
Your Laptop
     |
     ↓
minikube ssh
     |
     ↓
Minikube Node
```
For a real cluster, node access depends on the infrastructure and
security configuration.

---
## 24. Accessing an Application Inside a Pod

Suppose our NGINX application is running inside:
```
nginx-pod
```
We can inspect the Pod and its IP using:
```
kubectl get pods -o wide
```
Example:
```
NAME        IP
nginx-pod   10.x.x.x
```
From an appropriate network location inside the cluster/node, the
application can be accessed using the Pod IP.

For example:
```
curl http://<pod-ip>
```
The exact accessibility of a Pod IP depends on where the request
originates and the cluster networking configuration.

Important: Pod IPs are generally ephemeral. For stable access to
applications, Kubernetes Services are used. Services will be
covered later.

---
## 25. Deleting a Pod

To delete a Pod:
```
kubectl delete pod nginx-pod
```
General syntax:
```
kubectl delete pod <pod-name>
```
Example:
```
kubectl delete pod nginx-pod
```
The Pod is then removed from the cluster.

---
## 26. Pod Logs

To see the output/logs generated by a container in a Pod:
```
kubectl logs nginx-pod
```
General syntax:
```
kubectl logs <pod-name>
```
This is very useful when an application is:

- Crashing
- Not responding
- Producing unexpected output
- Failing during startup

---
## 27. Debugging Pods

Two extremely important commands are:
```
kubectl describe pod <pod-name>
```
and:
```
kubectl logs <pod-name>
```
kubectl describe

Use it to understand the Kubernetes-level state.
```
Pod
 |
 ├── Events
 ├── Conditions
 ├── Node
 ├── Container
 └── Configuration
```
kubectl logs

Use it to understand what the application/container is printing.
```
Pod
 |
 └── Container
       |
       └── Application Logs
```

Easy way to remember
```
describe
   ↓
"What is Kubernetes saying about my Pod?"

logs
   ↓
"What is my application saying?"
```
