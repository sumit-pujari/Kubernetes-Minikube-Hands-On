# ☸️ Kubernetes Ingress

> Kubernetes Ingress + Practical Demo**

## 1. Why Do We Need Ingress?

We already learned that Kubernetes Services can expose applications.

For example, suppose we have:

```text
Internet
   |
   +----> Service 1 → App 1
   |
   +----> Service 2 → App 2
   |
   +----> Service 3 → App 3
```
If every application uses a separate LoadBalancer Service:
```
App 1 → LoadBalancer → IP 1
App 2 → LoadBalancer → IP 2
App 3 → LoadBalancer → IP 3
```
This creates two major problems:

**Cost** — multiple LoadBalancers can become expensive.
**Limited routing features** — traditional enterprise load balancers provide advanced routing features that a basic Kubernetes Service does not provide.

Examples of advanced routing features:

- Host/domain-based routing
- Path-based routing
- SSL/TLS termination
- Whitelisting/blacklisting
- Sticky sessions
- Advanced load-balancing rules

Ingress was introduced to solve these kinds of requirements.

---
## 2. What is Ingress?

Ingress is a Kubernetes resource used to manage external HTTP/HTTPS access to applications running inside the cluster.

Instead of exposing every application with a separate external LoadBalancer:
```
                Internet
                   |
       +-----------+-----------+
       |           |           |
       v           v           v
   Service-1   Service-2   Service-3
       |           |           |
      App-1       App-2       App-3
```
Ingress can act as a common entry point:
```
                 Internet
                    |
                    v
                 Ingress
                    |
          +---------+---------+
          |         |         |
          v         v         v
      Service-1  Service-2  Service-3
          |         |         |
         App-1     App-2     App-3
```
So multiple applications can be routed through a common entry point/IP.

---
## 3. Ingress vs Service

Service

Provides:

- Service discovery
- Load balancing
- Application exposure

Ingress

- Provides more advanced HTTP/HTTPS routing to Services.

Think:
```
Service
   ↓
Basic application exposure

Ingress
   ↓
Advanced HTTP/HTTPS routing
```
---
## 4. LoadBalancer vs Ingress

Suppose we have three applications.

Using LoadBalancer Services
```
App-1 → LoadBalancer → IP-1
App-2 → LoadBalancer → IP-2
App-3 → LoadBalancer → IP-3
```
Multiple external load balancers may be required.

Using Ingress

                 Ingress
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
     App-1       App-2       App-3

A single entry point can route requests to multiple Services.

This can reduce the number of external load-balancing resources required.

---
## 5. What is an Ingress Controller?

Creating an Ingress resource alone is not enough.

We also need an Ingress Controller.
```
Ingress Resource
       |
       v
Ingress Controller
       |
       v
Services
       |
       v
Pods
```
The Ingress resource contains the routing rules.

The Ingress Controller actually implements those rules.

## 8. Ingress Resource

An Ingress resource defines routing rules.

For example:
```
app.example.com
       |
       v
   frontend-service

api.example.com
       |
       v
   backend-service
```
The Ingress Controller reads these rules and routes incoming requests accordingly.

---
## 9. Host-Based Routing

Host-based routing means routing traffic based on the hostname.

Example:
```
app.example.com
      ↓
frontend-service

api.example.com
      ↓
backend-service
```
Conceptually:
```
                  Ingress
                     |
          +----------+----------+
          |                     |
          v                     v
 app.example.com        api.example.com
          |                     |
          v                     v
 frontend-service        backend-service
```
This is one of the routing methods demonstrated in the practical session.

---
## 10. Example Ingress YAML
```
apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: app-ingress

spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
```
The important part is:
```
host: app.example.com
```
which tells the Ingress which hostname this rule applies to.

Then:
```
service:
  name: frontend-service
```
specifies where the traffic should go.

---

## 11. Path-Based Routing

Ingress can also route traffic based on the URL path.

For example:
```
example.com/
      ↓
frontend-service

example.com/api
      ↓
backend-service
```
Diagram:
```
                  Ingress
                     |
          +----------+----------+
          |                     |
          v                     v
       /                     /api
        |                     |
        v                     v
 frontend-service       backend-service
```
This allows multiple applications to be accessed through the same domain.

---

## 12. TLS / HTTPS

Ingress can also be configured for TLS.

Instead of:
```
HTTP
```
we can use:
```
HTTPS
```
Conceptually:
```
Client
   |
 HTTPS
   |
   v
Ingress
   |
   v
Service
   |
   v
Pod
```
Ingress can therefore handle TLS-related configuration at the entry point.

## 14. /etc/hosts for Local Testing

When testing host-based routing locally, the hostname must resolve to the Minikube/Ingress address.

The demo uses the /etc/hosts file for this purpose.

For example:
```
<MINIKUBE-IP>    app.example.com
```
Find the Minikube IP:
```
minikube ip
```
Then add the mapping to:
```
/etc/hosts
```
Now the local machine can resolve:
```
app.example.com
```
to the Minikube address.
