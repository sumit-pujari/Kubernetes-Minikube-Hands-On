# ☸️ Kubernetes — ReplicaSet, Deployment & Auto Healing

> This section explains how Kubernetes manages Pods using ReplicaSets and
> Deployments, how replicas are maintained, how Deployments provide
> rolling updates and rollbacks, and how Kubernetes detects unhealthy
> applications using health probes.

---
## 1. The Problem With Managing Pods Directly

In the previous topic, we learned about Pods.

A Pod is the smallest deployable unit in Kubernetes.

For example:

```text
Kubernetes
     |
     ↓
    Pod
     |
     ↓
Container
```
We can create a Pod manually:
```
apiVersion: v1
kind: Pod

metadata:
  name: nginx-pod

spec:
  containers:
    - name: nginx
      image: nginx
```
But there is a problem.

**What happens if the Pod dies?**

Suppose:
```
Pod
 ↓
Running
```
Then the application crashes:
```
Pod
 ↓
❌ Failed
```
If we created the Pod directly, Kubernetes does not give us the full
application-management capabilities that we need for a production
workload.

We need something that can say:

"I always want 3 copies of this application running."

This is where **ReplicaSet** comes in.

---
## 2. What is a ReplicaSet?

A ReplicaSet is a Kubernetes resource that ensures that a specified
number of Pod replicas are running.

For example:

replicas: 3

means:

          ReplicaSet
               |
       ┌───────┼───────┐
       ↓       ↓       ↓
     Pod 1   Pod 2   Pod 3

The ReplicaSet continuously tries to maintain the desired number of
Pods.

---

## 3. Why Do We Need ReplicaSets?

Suppose we want:
```
3 Pods
```
Initially:
```
Pod 1
Pod 2
Pod 3
```
Now imagine Pod 2 crashes:
```
Pod 1 → Running
Pod 2 → ❌
Pod 3 → Running
```
The actual number of running Pods is now:
```
2
```
But our desired state is:
```
3
```
The ReplicaSet detects the difference.
```
Desired = 3
Actual  = 2
```
Therefore, it creates another Pod:
```
Pod 1 → Running
Pod 2 → ❌
Pod 3 → Running
Pod 4 → Running
```
Now:
```
Desired = 3
Actual  = 3
```
This is one of the fundamental ideas behind Kubernetes:
```
Desired State
      ↓
Compare
      ↓
Actual State
      ↓
Take corrective action
```
---
## 4. Desired State

Kubernetes is largely based on the concept of desired state.

For example:
```
spec:
  replicas: 3
```
This tells Kubernetes:

- I want three replicas of this workload.

Kubernetes continuously works toward maintaining that state.

Conceptually:

              Desired State
                   |
                   ↓
              replicas: 3
                   |
                   ↓
             Kubernetes
                   |
            ┌──────┼──────┐
            ↓      ↓      ↓
           Pod    Pod    Pod

If the actual state changes:
```
Desired = 3
Actual  = 2
```
Kubernetes attempts to reconcile the difference.

---
## 5. ReplicaSet and Auto Healing

ReplicaSets provide an important part of Kubernetes' self-healing
behavior.

Suppose:
```
ReplicaSet
    |
    ├── Pod 1
    ├── Pod 2
    └── Pod 3
```
Pod 2 is deleted:
```
ReplicaSet
    |
    ├── Pod 1
    ├── ❌ Pod 2
    └── Pod 3
```
The ReplicaSet detects that only two replicas remain.

It creates a replacement:
```
ReplicaSet
    |
    ├── Pod 1
    ├── Pod 3
    └── Pod 4
```
Notice that the ReplicaSet doesn't necessarily bring the original
Pod back.

It creates a **new Pod.**

This is important:

- Pods are disposable/ephemeral. Controllers such as ReplicaSets
maintain the desired number of Pods.

---
## 6. ReplicaSet YAML

A basic ReplicaSet can be defined like this:
```
apiVersion: apps/v1
kind: ReplicaSet

metadata:
  name: nginx-rs

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:

    metadata:
      labels:
        app: nginx

    spec:
      containers:
        - name: nginx
          image: nginx
          ports:
            - containerPort: 80
```
**apiVersion**
```
apiVersion: apps/v1
```
This specifies the Kubernetes API version.

ReplicaSets use:
```
apps/v1
```

**kind**
```
kind: ReplicaSet
```
This tells Kubernetes that we are creating a ReplicaSet.

**metadata**
```
metadata:
  name: nginx-rs
```
This gives the ReplicaSet its name.

**replicas**
```
replicas: 3
```
This specifies the desired number of Pods.
```
replicas: 3
       ↓
     Pod 1
     Pod 2
     Pod 3
```
---
## 7. ReplicaSet Selectors and Labels

Two very important concepts are:

- Labels
- Selectors

The ReplicaSet needs a way to identify which Pods belong to it.

Example:
```
selector:
  matchLabels:
    app: nginx
```
and the Pod template has:
```
template:
  metadata:
    labels:
      app: nginx
```
The values must match.
```
ReplicaSet Selector
       |
       | app = nginx
       ↓
Pods with:
app = nginx
```
---
## 8. What is a Label?

A label is a key-value pair attached to a Kubernetes object.

Example:
```
labels:
  app: nginx
```
Here:
```
key   = app
value = nginx
```
Labels help Kubernetes organize and identify resources.

Examples:
```
labels:
  app: frontend
  environment: production
  team: payments
```
---
## 9. What is a Selector?

A selector is used to select resources based on their labels.

Example:
```
selector:
  matchLabels:
    app: nginx
```
This means:

- Select resources having the label app=nginx.

The relationship is:
```
Labels
   ↓
Attached to Pods

Selector
   ↓
Finds matching Pods
```
---
## 10. ReplicaSet Template

The template section describes the Pods that the ReplicaSet should
create.

Example:
```
template:
  metadata:
    labels:
      app: nginx

  spec:
    containers:
      - name: nginx
        image: nginx
```
Think of it as:
```
ReplicaSet
    |
    ↓
Pod Template
    |
    ↓
Create Pods
```
If we specify:
```
replicas: 3
```
the ReplicaSet creates three Pods from the template.

---
## 11. Creating a ReplicaSet

Save the YAML as:
```
replicaset.yaml
```
Then:
```
kubectl apply -f replicaset.yaml
```
Check the ReplicaSet:
```
kubectl get replicasets
```
or:
```
kubectl get rs
```
Check the Pods:
```
kubectl get pods
```
You should see multiple Pods.

Example:
```
NAME             READY   STATUS    RESTARTS   AGE
nginx-rs-abc12   1/1     Running   0          10s
nginx-rs-def34   1/1     Running   0          10s
nginx-rs-ghi56   1/1     Running   0          10s
```
---
## 12. Scaling a ReplicaSet

Suppose we currently have:
```
replicas: 3
```
We can change it to:
```
replicas: 5
```
Then Kubernetes will create additional Pods.

Before:
```
Pod 1
Pod 2
Pod 3
```

After:
```
Pod 1
Pod 2
Pod 3
Pod 4
Pod 5
```
You can also scale from the command line:
```
kubectl scale replicaset nginx-rs --replicas=5
```
Check:
```
kubectl get pods
```
---
## 13. Scaling Down

Suppose:
```
replicas: 5
```
and we change it to:
```
replicas: 2
```
Kubernetes removes excess Pods.
```
5 Pods
  ↓
replicas = 2
  ↓
2 Pods remain
```
The ReplicaSet always tries to maintain the configured number.

---
## 14. Limitations of ReplicaSet

ReplicaSets are useful, but they are not normally the resource we
directly use to manage application releases.

ReplicaSets can maintain:

- Desired number of Pods
- Pod replacement
- Basic scaling

But application deployment also requires:

- Rolling updates
- Rollbacks
- Version management
- Release management

This is where **Deployment** comes in.

---
## 15. What is a Deployment?

A Deployment is a higher-level Kubernetes resource used to manage
application Pods and ReplicaSets.

The relationship is:
```
Deployment
     |
     ↓
ReplicaSet
     |
     ↓
   Pods
     |
     ↓
Containers
```
This hierarchy is extremely important.

Remember:
```
Deployment
    ↓
ReplicaSet
    ↓
   Pod
    ↓
Container
```
A Deployment manages the ReplicaSet, and the ReplicaSet manages the
Pods.

---
## 16. Why Do We Need Deployments?

Suppose we have an application running:
```
nginx:v1
```
Now we release:
```
nginx:v2
```
We need a safe way to update the running application.

We don't want to:
```
Delete all old Pods
       ↓
Create all new Pods
```
because that can cause downtime.

Instead, Kubernetes can gradually replace old Pods with new Pods.

This is called a:

***Rolling Update***

---
## 17. Deployment Architecture

The complete architecture is:

                  Deployment
                       |
                       ↓
                 ReplicaSet
                       |
             ┌─────────┼─────────┐
             ↓         ↓         ↓
           Pod       Pod       Pod
             |         |         |
             ↓         ↓         ↓
        Container  Container  Container

When the application version changes:
```
Deployment
     |
     ├── Old ReplicaSet
     |      |
     |      ├── Old Pod
     |      └── Old Pod
     |
     └── New ReplicaSet
            |
            ├── New Pod
            └── New Pod
```
The Deployment manages the transition between versions.

---
## 18. Deployment YAML

A basic Deployment:
```
apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx-deployment

spec:
  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:

    metadata:
      labels:
        app: nginx

    spec:
      containers:
        - name: nginx
          image: nginx:latest
          ports:
            - containerPort: 80
```
---

Deployments can also be scaled.

Suppose:
```

```
5 replicas
```
Using:
```

```
Then:
```

## 22. Deployment vs ReplicaSet vs Pod

This is one of the most important comparisons.
| Feature                | Pod               | ReplicaSet   | Deployment               |
| ---------------------- | ----------------- | ------------ | ------------------------ |
| Runs containers        | Yes               | Through Pods | Through ReplicaSets/Pods |
| Smallest workload unit | Yes               | No           | No                       |
| Maintains replicas     | No                | Yes          | Yes                      |
| Auto replacement       | Limited by itself | Yes          | Yes, through ReplicaSet  |
| Rolling updates        | No                | No           | Yes                      |
| Rollback               | No                | No           | Yes                      |
| Scaling                | Manual recreation | Yes          | Yes                      |
| Version management     | No                | Limited      | Yes                      |

**Easy memory trick**
```
Pod
 ↓
Runs application

ReplicaSet
 ↓
Maintains number of Pods

Deployment
 ↓
Manages ReplicaSets and application releases
```

## 23. Rolling Updates

Suppose the current application is:
```
nginx:v1
```
and we want:
```
nginx:v2
```
A Deployment can perform a rolling update.

Instead of replacing everything at once:
```
Old version
Pod 1
Pod 2
Pod 3
```
Kubernetes gradually creates the new version:
```
Old Pod 1
Old Pod 2
New Pod 1
```
then:
```
Old Pod 2
New Pod 1
New Pod 2
```
and eventually:
```
New Pod 1
New Pod 2
New Pod 3
```
The exact rollout behavior depends on the Deployment strategy and
configuration.

---
## 24. Why Rolling Updates Are Useful

Rolling updates help reduce downtime during application deployments.

Instead of:
```
Delete everything
      ↓
Deploy everything
```
we do:
```
Old version
     ↓
Gradually replace
     ↓
New version
```
This is especially useful for production applications.

---
## 25. Updating an Image

Suppose the Deployment currently uses:
```
image: nginx:1.25
```
We want:
```
image: nginx:1.26
```
We can update the Deployment manifest and apply it:
```
kubectl apply -f deployment.yaml
```
Kubernetes detects the change and performs a rollout.

You can also use:
```
kubectl set image deployment/nginx-deployment \
  nginx=nginx:1.26
```
Then check:
```
kubectl rollout status deployment/nginx-deployment
```
**Checking rollout status

This allows you to monitor whether the rollout has completed.

Conceptually:
```
Deployment Update
       |
       ↓
New ReplicaSet
       |
       ↓
New Pods
       |
       ↓
Old Pods gradually removed
       |
       ↓
Rollout Complete
```
---
## 26. Rollback

Sometimes a new application version introduces a bug.

For example:
```
v1 → Stable
v2 → Buggy
```
We need to return to the previous version.

This is called a rollback.

Kubernetes Deployments maintain rollout history that can be used to
roll back to an earlier revision.

Command:
```
kubectl rollout undo deployment/nginx-deployment
```
Conceptually:
```
v1
 ↓
v2
 ↓
❌ Bug
 ↓
Rollback
 ↓
v1
```
---
## 27. Deployment History

To see the rollout history:
```
kubectl rollout history deployment/nginx-deployment
```
This can help you understand which revisions have been created.

Conceptually:
```
Revision 1 → nginx:v1
Revision 2 → nginx:v2
Revision 3 → nginx:v3
```
You can then roll back if required.

---
## 28. ReplicaSet During a Deployment Update

This is an important concept.

Suppose:
```
Deployment
     |
     ↓
ReplicaSet v1
     |
     ├── Pod
     ├── Pod
     └── Pod
```
After changing the image:
```
Deployment
     |
     ├── ReplicaSet v1
     |      └── Old Pods
     |
     └── ReplicaSet v2
            └── New Pods
```
The Deployment controls the transition between ReplicaSets.

Therefore:
```
Deployment
   |
   ├── Old ReplicaSet
   |
   └── New ReplicaSet
```
This is how Deployments support versioned application updates.

## 29. What is Auto Healing?

Auto healing means Kubernetes can automatically take corrective
action when an application or workload becomes unhealthy.

For example:
```
Application
     |
     ↓
Pod
     |
     ↓
❌ Failure
     |
     ↓
Kubernetes detects problem
     |
     ↓
Corrective action
````
Depending on what failed and which controller/probe is involved,
Kubernetes may:

- Restart a container
- Stop routing traffic to an unhealthy Pod
- Replace a failed Pod
- Maintain the desired number of replicas

  
**Health Checks** 

Kubernetes provides health-check mechanisms called probes.

The three main probes are:
```
Probes
  |
  ├── Readiness Probe
  |
  ├── Liveness Probe
  |
  └── Startup Probe
```

Each has a different purpose.
