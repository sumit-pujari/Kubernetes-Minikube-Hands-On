## 3. Application Deployment Flow

The application is deployed into Kubernetes using a Deployment.

The basic flow is:
```
Docker Image
     |
     v
Deployment
     |
     v
ReplicaSet
     |
     v
Pods
```
For example:
```
Docker Image
     |
     v
Kubernetes Deployment
     |
     v
ReplicaSet
     |
     +---------+---------+
     |         |         |
     v         v         v
   Pod-1     Pod-2     Pod-3
```
A healthy environment should show that the required Minikube components are running.

## 4. Deployment → ReplicaSet → Pod

A Deployment does not directly manage the individual containers.

The relationship is:
```
Deployment
     |
     v
ReplicaSet
     |
     v
Pods
     |
     v
Containers
```
Suppose the Deployment specifies:
```
spec:
  replicas: 2
```
Kubernetes tries to maintain:
```
Pod-1
Pod-2
```
If Pod-1 is deleted:
```
Pod-1 ❌
Pod-2
```
The ReplicaSet notices that:
```
Desired = 2
Current = 1
```
and creates another Pod:
```
Pod-2
Pod-3
```
The new Pod gets a new IP address.

This is important for understanding why Services are required.

## 5. Pod IP Address

Every Pod gets an IP address from the Kubernetes cluster network.

For example:
```
Pod-1
IP = 10.244.0.5
```
```
Pod-2
IP = 10.244.0.6
```
You can see Pod IPs using:
```
kubectl get pods -o wide
```
Example:
```
NAME       READY   STATUS    IP
app-pod1   1/1     Running   10.244.0.5
app-pod2   1/1     Running   10.244.0.6
```

## 6. Why Direct Pod IP Access Is a Problem

Suppose we directly access:
```
10.244.0.5
```
The request reaches:
```
Pod-1
```
But now Pod-1 gets deleted.
```
Pod-1 ❌
```
ReplicaSet creates:
```
Pod-3
```
with:
```
IP = 10.244.0.10
```
Now:
```
Old Pod:
10.244.0.5
```
```
New Pod:
10.244.0.10
```
If the client was using:
```
10.244.0.5
```
the client cannot simply depend on that IP forever.

## 7. Service Discovery
What is Service Discovery?

Service Discovery is the mechanism through which applications find the correct Pods without depending directly on dynamic Pod IP addresses.

Instead of:
```
Application
     |
     v
Pod IP
```
we use:
```
Application
     |
     v
Service
     |
     v
Matching Pods
```
Example

Suppose we have:
```
Pod-1 → 10.244.0.5
Pod-2 → 10.244.0.6
Pod-3 → 10.244.0.7
```
Instead of remembering:
```
10.244.0.5
10.244.0.6
10.244.0.7
```
the application communicates with:
```
payment-service
```
The Service finds the correct Pods.

This is the fundamental reason we need Service Discovery.

## 8. Labels and Selectors

This is one of the most important concepts in Kubernetes Services.

A Pod can have labels:
```
metadata:
  labels:
    app: payment
```
Example:
```
Pod-1
label:
  app=payment
Pod-2
label:
  app=payment
```
The Service uses a selector:
```
selector:
  app: payment
```
The Service then finds:
```
Pod-1
Pod-2
```
because both have:
```
app=payment
```

Visual Representation

                  Service
                     |
              selector:
              app=payment
                     |
          +----------+----------+
          |                     |
          v                     v
       Pod-1                  Pod-2
    app=payment            app=payment

## 9. Creating a Kubernetes Service

A basic Service can be created using YAML.

Example:
```
apiVersion: v1
kind: Service

metadata:
  name: demo-service

spec:
  selector:
    app: demo

  ports:
    - port: 80
      targetPort: 8000
```
Apply it:
```
kubectl apply -f service.yaml
```
Check it:
```
kubectl get svc
```
Describe it:
```
kubectl describe svc demo-service
```

## 10. Understanding Service Ports

This is very important when creating Services.

Consider:
```
ports:
  - port: 80
    targetPort: 8000
```
There are two different ports.
```
port
port: 80
```
This is the port exposed by the Service.
```
targetPort
targetPort: 8000
```
This is the port where the application is actually listening.

For example, if the Python application runs on:
```
8000
```
then:
```
targetPort: 8000
```
must point to that application port.

Traffic Flow
```
Client
  |
  | Service Port 80
  v
Service
  |
  | targetPort 8000
  v
Pod
  |
  v
Application :8000
```

## 11. ClusterIP

ClusterIP is the default Kubernetes Service type.

It provides an internal stable endpoint.

Example:
```
apiVersion: v1
kind: Service

metadata:
  name: demo-service

spec:
  type: ClusterIP

  selector:
    app: demo

  ports:
    - port: 80
      targetPort: 8000
```
Architecture:

             Kubernetes Cluster
                    |
                    v
              ClusterIP
                    |
          +---------+---------+
          |         |         |
          v         v         v
        Pod-1     Pod-2     Pod-3

ClusterIP is mainly used for communication within the cluster.

For example:
```
Frontend Pod
     |
     v
Backend Service
     |
     v
Backend Pods
```

## 12. NodePort

NodePort exposes a Service through a port on the Kubernetes worker node.

Example:
```
apiVersion: v1
kind: Service

metadata:
  name: demo-service

spec:
  type: NodePort

  selector:
    app: demo

  ports:
    - port: 80
      targetPort: 8000
      nodePort: 30007
```
The application can then be reached using:
```
<NodeIP>:30007
```
Example:
```
192.168.49.2:30007
```
For Minikube, you can obtain the node IP using:
```
minikube ip
```

NodePort Traffic Flow
```
User
 |
 | NodeIP:30007
 v
Worker Node
 |
 v
NodePort
 |
 v
Service
 |
 +--------+--------+
 |        |        |
 v        v        v
Pod-1   Pod-2    Pod-3
```

## 15. Service Discovery Failure Demo

This is one of the most useful practical demonstrations.

Suppose Pods have:
```
labels:
  app: demo
```
And Service has:
```
selector:
  app: demo
```

Everything works.
```
Service
   |
   | selector app=demo
   |
   +----> Pod-1
   +----> Pod-2
````

Now Change the Selector

Suppose we change the Service selector to:
```
selector:
  app: backend
```
But the Pods still have:
```
labels:
  app: demo
```
Now:
```
Service selector:
app=backend
```
```
Pod labels:
app=demo
```
They do not match.

Therefore:
```
Service
   |
   | app=backend
   |
   X
   |
No matching Pods
```

Traffic cannot reach the expected Pods.

Important Rule

Service selector must match Pod labels.
```
Service selector
        =
Pod label
```
Example:
```
Service:
selector:
  app: payment

Pod:
labels:
  app: payment
```
Correct.

## 16. Why Labels Are So Important

Labels are not just for identification.

They are used by many Kubernetes resources to select objects.

For Services:
```
Service
   |
   v
Selector
   |
   v
Pod Labels
```

For Deployments:
```
Deployment
   |
   v
Pod Template Labels
```
This means incorrect labels/selectors can cause major problems.

For example:
```
Application is running
        +
Pods are healthy
        +
Service exists
        +
Service selector is wrong
        =
Application still unreachable
```

This is a very common Kubernetes troubleshooting issue.

## Practical Debugging Workflow

Suppose your Service is not working.

Do not randomly change YAML.

Follow a systematic process.

Step 1 — Check Pods
```
kubectl get pods
```
Check:

- STATUS
- READY
- RESTARTS
  
Step 2 — Check Pod IPs
```
kubectl get pods -o wide
```
Check:

- Pod IP
- Node
- Status
- 
Step 3 — Check Deployment
```
kubectl get deployment
```
Then:
```
kubectl describe deployment <deployment-name>
```
Step 4 — Check Service
```
kubectl get svc
```
Then:
```
kubectl describe svc <service-name>
```
Step 5 — Check Selector

Look at:
```
selector:
  app: demo
```
Step 6 — Check Pod Labels
```
kubectl get pods --show-labels
```
Verify:
```
Service selector
        |
        v
Pod labels
```
match.

Step 7 — Check Endpoints / EndpointSlices

Depending on your Kubernetes version, inspect the backend endpoints using:
```
kubectl get endpoints <service-name>
```
or:
```
kubectl get endpointslice
```
If the Service has no matching backend endpoints, investigate:

- Selector
- Labels
- Pod readiness
- Service configuration
  
Step 8 — Test the Application

Use:
```
curl
```
or another HTTP client.

For example:
```
curl http://<service-address>
```

## kubectl edit

The video demonstrates modifying a Service directly using:
```
kubectl edit svc <service-name>
```
This opens the resource for editing.

For example:
```
kubectl edit svc demo-service
```
You might change:
```
selector:
  app: demo
```
to:
```
selector:
  app: backend
```
If no Pods have:
```
app=backend
```
the Service will no longer have the expected backend targets.

## Kubernetes API Server Verbose Mode

A useful trick demonstrated in the practical session is the -v flag.

Example:
```
kubectl get pods -v=7
```
Higher verbosity can show more information about what kubectl is doing.

For example:
```
kubectl get pods -v=9
```
can provide very detailed HTTP/API communication information.

## What Happens When You Run kubectl get pods?

When you execute:
```
kubectl get pods
```
the basic flow is:
```
kubectl
   |
   v
kubeconfig
   |
   v
API Server
   |
   v
Kubernetes API
   |
   v
Pod information
   |
   v
kubectl displays result
```
Verbose output can help you understand this communication.

---
## Why -v=7 or -v=9 Is Useful

Suppose you are debugging a Kubernetes client/API issue.

Instead of only seeing:
```
Error
```
you can inspect more details about:

- API endpoint
- HTTP request
- HTTP response
- Authentication context
- API calls

Example:
```
kubectl get pods -v=7
```
This is useful when learning how kubectl communicates with the API Server.
