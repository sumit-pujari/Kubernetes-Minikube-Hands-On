## 1. What is RBAC?

**RBAC = Role-Based Access Control**

RBAC controls:

> **Who can perform what actions on which Kubernetes resources?**

For example:

```text
Developer
   |
   | Can:
   | - get Pods
   | - list Pods
   | - view Deployments
   |
   X Cannot:
     - delete Pods
     - create Deployments
```
RBAC is used to control access to Kubernetes resources.

---
## 2. Why Do We Need RBAC?

Imagine a company has:

- Admin
- Developer
- Tester
- DevOps Engineer

Everyone should not have the same permissions.

For example:
```
Developer
   ↓
Read Pods
Read Logs
Read Services

DevOps
   ↓
Create Deployments
Update Services
Delete Pods

Admin
   ↓
Full cluster access
```
Without access control, users could perform operations they should not be allowed to perform.

RBAC follows the principle:

> **Give users only the permissions they need.**

## 3. Kubernetes RBAC Components

The main RBAC objects are:

- Role
- ClusterRole
- RoleBinding
- ClusterRoleBinding

Think of them as:
```
Role / ClusterRole
        ↓
"What can be done?"

RoleBinding / ClusterRoleBinding
        ↓
"Who can do it?"
```
---
## 4. Role

A Role defines permissions within a specific Namespace.

Example:
```
apiVersion: rbac.authorization.k8s.io/v1
kind: Role

metadata:
  name: pod-reader
  namespace: development

rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
```
This Role allows:
```
get Pods
list Pods
```
inside the development namespace.

It does NOT automatically provide access to Pods in other namespaces.

---
## 5. Common RBAC Fields
`resources`

Defines what Kubernetes resources can be accessed.

Examples:
```
pods
services
deployments
configmaps
secrets
```

`verbs`

Defines what actions are allowed.

Common verbs:
```
get
list
watch
create
update
patch
delete
```
Example:
```
verbs:
  - get
  - list
```
means the user can read resources but cannot modify them.

---

## 6. RoleBinding

Creating a Role does not give anyone permission by itself.

We need to bind the Role to a user/group/service account.

Example:
```
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding

metadata:
  name: read-pods
  namespace: development

subjects:
  - kind: User
    name: developer

roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```
Now:
```
developer
    |
    v
RoleBinding
    |
    v
pod-reader Role
    |
    v
Can get/list Pods
```
---
## 7. Role vs RoleBinding

Remember:
```
Role
 ↓
Defines permissions

RoleBinding
 ↓
Assigns those permissions to a user/group/service account
```
A Role without a binding does not grant those permissions to a user.

---
## 8. ClusterRole

A ClusterRole defines permissions at the cluster level.

It can be used for:

- Cluster-wide resources
- Resources across namespaces when bound appropriately

Example:
```
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole

metadata:
  name: pod-reader

rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list"]
```
---

## 9. ClusterRoleBinding

ClusterRoleBinding connects a ClusterRole to a user/group/service account at the cluster level.
```
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding

metadata:
  name: pod-reader-binding

subjects:
  - kind: User
    name: developer

roleRef:
  kind: ClusterRole
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```
Conceptually:
```
User
 |
 v
ClusterRoleBinding
 |
 v
ClusterRole
 |
 v
Permissions
```
---

## 10. Role vs ClusterRole

| Role                                    | ClusterRole                         |
| --------------------------------------- | ----------------------------------- |
| Namespace-scoped                        | Cluster-level RBAC object           |
| Used for permissions within a namespace | Can define cluster-wide permissions |
| Used with RoleBinding                   | Used with ClusterRoleBinding        |
| Good for namespace-specific access      | Good for broader access             |


Easy memory:
```
Role
 ↓
Namespace

ClusterRole
 ↓
Cluster
```
---

## 11. RoleBinding vs ClusterRoleBinding
```
RoleBinding
     ↓
Grants Role permissions within a namespace

ClusterRoleBinding
     ↓
Grants ClusterRole permissions cluster-wide
```

## 13. Checking RBAC Permissions

A very useful command is:
```
kubectl auth can-i
```
Example:
```
kubectl auth can-i get pods
```
Possible output:
```
yes
```
or:
```
no
```
You can check a specific user:
```
kubectl auth can-i get pods --as=developer
```
Check whether the user can delete Pods:
```
kubectl auth can-i delete pods --as=developer
```
This is extremely useful when troubleshooting RBAC permissions.

## 14. Important RBAC Commands
View Roles
```
kubectl get roles
```
View ClusterRoles
```
kubectl get clusterroles
```
View RoleBindings
```
kubectl get rolebindings
```
View ClusterRoleBindings
```
kubectl get clusterrolebindings
```
Describe Role
```
kubectl describe role <role-name>
```
Describe RoleBinding
```
kubectl describe rolebinding <binding-name>
```
Check permission
```
kubectl auth can-i get pods
```
Check permission as another user
```
kubectl auth can-i get pods --as=developer
```
