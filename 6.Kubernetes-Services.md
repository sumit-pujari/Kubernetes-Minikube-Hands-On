# ☸️ Kubernetes Services

> Everything About Kubernetes Services | Service Discovery | Load Balancing | Networking**

## 1. Why Do We Need Kubernetes Services?

Before understanding Service, remember what we learned about Deployments.

A Deployment creates Pods through ReplicaSets.

For example:

```text
Deployment
    |
    v
ReplicaSet
    |
    +----------+----------+
    |          |          |
    v          v          v
  Pod-1      Pod-2      Pod-3
```
Suppose our application has 3 replicas:
```
Pod-1 → 10.244.0.5
Pod-2 → 10.244.0.6
Pod-3 → 10.244.0.7
```
Now imagine Pod-2 crashes.

Kubernetes automatically creates a replacement Pod:
```
Pod-1 → 10.244.0.5
Pod-2 → ❌
Pod-3 → 10.244.0.7
Pod-4 → 10.244.0.10
```
Notice something important:

The replacement Pod has a **different IP address.**

This creates a problem.

---
## 2. The Problem With Pod IP Addresses
**Problem 1 — Pod IPs are not stable**

Pods are temporary/ephemeral resources.

A Pod can:

- crash
- be deleted
- be recreated
- be rescheduled to another node
- be replaced during scaling

Therefore, its IP address can change.

Example:

Before:
```
payment-pod
IP = 10.244.0.5
```
Pod crashes.

After:
```
new-payment-pod
IP = 10.244.0.12
```
The application that was communicating with:
```
10.244.0.5
```
cannot continue depending on that IP.

**Problem 2 — Multiple Pods have multiple IP addresses**

Suppose we have:
```
payment-pod-1 → 10.244.0.5
payment-pod-2 → 10.244.0.6
payment-pod-3 → 10.244.0.7
```
Should the client remember all these IP addresses?

No.

Imagine having 100 replicas:
```
Pod-1   → IP-1
Pod-2   → IP-2
Pod-3   → IP-3
...
Pod-100 → IP-100
```
This would be extremely difficult to manage.

**Problem 3 — How do users access the application?**

Suppose we deploy:

> Frontend

> Backend

> Payment

> Database

The users should not need to know the individual Pod IP addresses.

We need a stable way to access the application.

That is where Kubernetes Service comes into the picture.

---

## 3. What is a Kubernetes Service?

A Service provides a stable network endpoint to access a group of Pods.

In simple words:

A Service is a stable entry point that forwards traffic to the appropriate Pods.

Instead of:
```
Client
  |
  +----> Pod-1 IP
  +----> Pod-2 IP
  +----> Pod-3 IP
```
we use:
```
Client
   |
   v
Service
   |
   +------> Pod-1
   +------> Pod-2
   +------> Pod-3
```
The client only needs to know the Service.

## 4. How Service Solves the Problem

Without Service:
```
Client
  |
  v
Pod IP
```
If the Pod dies:
```
Pod IP changes
     |
     v
Client loses connection
```
With Service:
```
Client
  |
  v
Service
  |
  +----> Pod-1
  +----> Pod-2
  +----> Pod-3
```
If Pod-2 dies:
```
Client
  |
  v
Service
  |
  +----> Pod-1
  +----> Pod-3
  +----> New Pod
```
The client does not need to know what happened.

The Service continues providing a stable endpoint.

## 5. Service Discovery

One of the most important concepts in this topic is:
```
Service Discovery
```
Service Discovery means:

Finding the correct application/service without manually tracking changing Pod IP addresses.

Suppose we have:
```
payment-pod-1
payment-pod-2
payment-pod-3
```
Each Pod can have a different IP.

Instead of remembering the IPs, Kubernetes uses a Service name.

For example:
```
payment
```
Applications can communicate using the Service name.

**Service DNS**

Inside Kubernetes, a Service can be accessed using DNS.

For example:
```
payment
```
or:
```
payment.default.svc
```
More generally:
```
<service-name>.<namespace>.svc
```
Example:
```
payment.default.svc
```
Here:
```
payment
    ↓
Service name

default
    ↓
Namespace

svc
    ↓
Indicates Kubernetes Service
```
The important idea is:
```
Application
     |
     v
Service Name
     |
     v
Kubernetes Service
     |
     v
Correct Pod
```
The application does not need to know the changing Pod IP addresses.

## 6. Labels and Selectors

This is one of the most important concepts for understanding how a Service knows which Pods to send traffic to.

Kubernetes uses:

- Labels
- Selectors
  
**Labels**

A label is metadata attached to a Kubernetes object.

Example:
```
metadata:
  labels:
    app: payment
```
So a Pod might have:
```
Pod-1
label:
    app=payment
```
Another Pod:
```
Pod-2
label:
    app=payment
```
Another:
```
Pod-3
label:
    app=payment
```

**Selector**

A Service can say:

Find all Pods where:
```
app = payment
```
Example:
```
selector:
  app: payment
```
The Service will select Pods matching that label.

**Label + Selector Relationship**
```
                Service
                   |
                   |
             selector:
             app=payment
                   |
        +----------+----------+
        |          |          |
        v          v          v
      Pod-1      Pod-2      Pod-3
   app=payment app=payment app=payment
```

The Service does not care whether the Pod IP is:
```
10.244.0.5
10.244.0.6
10.244.0.20
```
It cares about the label:
```
app=payment
```

## 7. Service and Multiple Pods

Suppose a Deployment creates three replicas:
```
Deployment
     |
     v
ReplicaSet
     |
     +----------+----------+
     |          |          |
     v          v          v
   Pod-1      Pod-2      Pod-3
```
Each Pod gets a unique IP:
```
Pod-1 → 10.244.0.5
Pod-2 → 10.244.0.6
Pod-3 → 10.244.0.7
```

Now create a Service:
```
payment-service
```
with:
```
selector:
  app: payment
```
All matching Pods become the targets of that Service.

                  payment-service
                        |
             selector: app=payment
                        |
          +-------------+-------------+
          |             |             |
          v             v             v
       Pod-1          Pod-2          Pod-3
       10.5           10.6           10.7
       
## 8. Load Balancing

Another major responsibility of Services is load balancing.

Suppose we have:

             Service
                |
       +--------+--------+
       |        |        |
       v        v        v
     Pod-1    Pod-2    Pod-3

And 3 requests arrive:
```
Request 1
Request 2
Request 3
```
The Service can distribute traffic across the available Pods.

Conceptually:
```
Request 1 ─────> Pod-1

Request 2 ─────> Pod-2

Request 3 ─────> Pod-3
```
This prevents all requests from being sent to only one Pod.

Why Load Balancing is Needed

Suppose:
```
1000 requests
```
and we have:
```
Pod-1
Pod-2
Pod-3
```
Instead of:
```
1000 requests
       |
       v
     Pod-1
```
we want traffic distributed among replicas.

             Service
                |
        +-------+-------+
        |       |       |
        v       v       v
      Pod-1   Pod-2   Pod-3

This allows multiple replicas to serve users concurrently.

## 9. How a Service Finds Pods

The basic mechanism is:
```
Service
   |
   | selector
   v
Labels on Pods
   |
   v
Matching Pods
```
Example:
```
Pods
Pod-1:
  app: payment

Pod-2:
  app: payment

Pod-3:
  app: frontend
Service
selector:
  app: payment
```
Result:
```
Service
   |
   +----> Pod-1
   |
   +----> Pod-2
```
```
Pod-3 is ignored
because:

app=frontend
```

## 10. Types of Kubernetes Services

Kubernetes provides different Service types depending on who should be able to access the application.

The three important types covered here are:

- ClusterIP
- NodePort
- LoadBalancer

Think about them based on accessibility.

                    Kubernetes Cluster
                           |
             +-------------+-------------+
             |             |             |
          ClusterIP     NodePort     LoadBalancer
             |             |             |
          Internal      Network       External
          access        access        access

---
## 11. ClusterIP
**What is ClusterIP?**

ClusterIP is the default Service type.

It allows access to the application from inside the Kubernetes cluster.

Example:
```
Pod A
  |
  v
payment-service
  |
  v
Payment Pods
```
Another application inside the cluster can communicate with:
```
payment-service
```
ClusterIP Diagram

              Kubernetes Cluster
        +----------------------------+
        |                            |
        |   Frontend Pod             |
        |       |                    |
        |       v                    |
        |  payment-service           |
        |       |                    |
        |       +----> Pod-1         |
        |       +----> Pod-2         |
        |       +----> Pod-3         |
        |                            |
        +----------------------------+

External users cannot directly access the ClusterIP Service from the public internet.

**ClusterIP Example**
```
apiVersion: v1
kind: Service

metadata:
  name: payment-service

spec:
  type: ClusterIP

  selector:
    app: payment

  ports:
    - port: 80
      targetPort: 8080
```
ClusterIP is actually the default, so this can also be written without:
```
type: ClusterIP
```
---
## 12. NodePort

Sometimes we need to expose the application outside the cluster but do not want to create a cloud Load Balancer.

For this we can use:
```
NodePort
```
NodePort exposes the Service through a port on the Kubernetes worker nodes.

**NodePort Architecture**
```
External User
      |
      v
Worker Node IP
      |
      v
NodePort
      |
      v
Service
      |
      +--------+--------+
      |        |        |
      v        v        v
    Pod-1    Pod-2    Pod-3
```
The user accesses something conceptually like:
```
<NodeIP>:<NodePort>
```
Example:
```
192.168.1.10:30080
```

**NodePort Example**
```
apiVersion: v1
kind: Service

metadata:
  name: payment-service

spec:
  type: NodePort

  selector:
    app: payment

  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
```
Now the application can be accessed using:
```
<NodeIP>:30080
```
---
## 13. LoadBalancer

LoadBalancer is generally used when we want to expose an application externally using a cloud provider's load balancer.

For example:
```
AWS
Azure
GCP
```
can integrate with Kubernetes to provision an external load balancer.

**LoadBalancer Architecture**

              Internet
                 |
                 v
        External Load Balancer
                 |
                 v
            Kubernetes
                 |
              Service
                 |
        +--------+--------+
        |        |        |
        v        v        v
      Pod-1    Pod-2    Pod-3

The cloud provider provisions an external endpoint.

Users can access the application through that external endpoint.

**LoadBalancer Example**
```
apiVersion: v1
kind: Service

metadata:
  name: payment-service

spec:
  type: LoadBalancer

  selector:
    app: payment

  ports:
    - port: 80
      targetPort: 8080
```
On a supported cloud environment, Kubernetes requests an external load balancer from the cloud provider.

---
## 14. ClusterIP vs NodePort vs LoadBalancer
| Service Type   | Accessible From               | Main Purpose                                 |
| -------------- | ----------------------------- | -------------------------------------------- |
| `ClusterIP`    | Inside cluster                | Internal communication                       |
| `NodePort`     | Through worker node IP + port | Expose application through node              |
| `LoadBalancer` | External/public clients       | Expose application using cloud load balancer |

**Easy Way to Remember**
```
ClusterIP
    ↓
Inside Cluster

NodePort
    ↓
Through Node IP + Port

LoadBalancer
    ↓
External/Public Access
```

## Useful kubectl Commands
Get all Services
```
kubectl get services
```
or:
```
kubectl get svc
```
Get Services in all namespaces
```
kubectl get svc -A
```
Describe a Service
```
kubectl describe service payment-service
```
or:
```
kubectl describe svc payment-service
```
This helps understand:

- Service type
- ClusterIP
- Ports
- Selector
- Endpoints
- Events
  
Create Service from YAML
```
kubectl apply -f service.yaml
```
Delete Service
```
kubectl delete service payment-service
```
Get Service in YAML format
```
kubectl get svc payment-service -o yaml
```
Get Service in wide output
```
kubectl get svc -o wide
```
